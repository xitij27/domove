# Issue #4: construction notifications

## What works now

The original MVP schedules local reminders for relevant obstacle events already supplied to the app. It provides per-route **1 Week Before**, **1 Day Before**, and **Disabled** settings; Disabled remains the default. This revision preserves those settings, adds a preferred notification time (default **09:00 device-local**), optional commuting days and departure time, and opt-in **Important Last-Minute Updates**. Settings remain in AsyncStorage under `@domove/construction-notifications/v1`; the reader migrates older preference-only records without deleting them. Saving Disabled cancels pending reminders and keeps the other choices for later re-enabling.

Reminder dates use local calendar days across daylight-saving changes. Date-only construction end dates remain valid through the end of that day. Invalid, ended, cancelled, or past reminders are skipped. When the preferred reminder time has passed, an immediate local alert is possible only if the route opted in, the obstacle source marks a **NEW** or **SIGNIFICANT_CHANGE** revision with a real `observedAt` within the previous 24 hours, and the work is still actionable. Delivered revision IDs persist locally to prevent repeat alerts. Optional commuting days filter only when the obstacle source supplies reliable `activeWeekdays`; departure time is saved as context but does not suppress alerts without construction-hour data.

The notification tray payload now contains route and obstacle IDs instead of a full route snapshot. Local storage keeps only the route labels and waypoints needed for offline directions, not coordinates or unrelated route fields. The Android channel requests private lock-screen visibility for new installations; users can also control notification previews in system settings. On tap, the app resolves the known event from local storage and builds a fixed Google Maps Directions HTTPS URL from validated route data. Already-delivered notifications from the previous MVP still open through their validated legacy payload. Google Maps receives origin, destination, travel mode, and up to three supported intermediate/detour waypoints; it may calculate a different path. No arbitrary URL from a notification is opened. The message shows estimated additional time only when the obstacle event supplies one; it never treats proximity alone as a proven disruption.

## Team integration

`src/notifications/model.ts` defines `NotificationRoute`, a structural subset of Issue #1's `SavedRoute`, plus `ConstructionObstacleEvent`. The temporary read-only route launcher reads Issue #1's `saved_routes` view; the routes teammate can place `<NotificationSettings route={savedRoute} onBack={...} />` on a saved-route card and remove the launcher afterward. Call `await constructionNotifications.forgetRoute(route.id)` **after confirmed deletion** to remove local settings/events and cancel reminders.

The obstacle teammate calls `await constructionNotifications.processObstacle(savedRoute, event)` only after its own route-relevance calculation confirms an impact. Required event fields: stable `routeId`, stable `obstacleId`, and real `constructionLocation`. Provide `constructionStartDate` as site-local `YYYY-MM-DD`; without it, the service keeps the event but schedules nothing. Optional fields: `constructionEndDate`, reliable `additionalMinutes`, `alternativeWaypoints` (ordered full replacement of intermediate stops), and reliable `activeWeekdays`. To enable last-minute alerts, supply a stable `revision`, actual ISO `observedAt`, and `change: 'NEW' | 'SIGNIFICANT_CHANGE'`; use `UNCHANGED` otherwise. `change: 'CANCELLED'` or `removeObstacle(routeId, obstacleId)` cancels pending reminders. Reprocessing the same IDs and revision is safe. Do not invent dates, detours, or relevance.

`src/notifications/remote.ts` is an **inactive integration boundary** for an authenticated push backend: `register(hasEnabledRoute)` requests permission and obtains an Expo Push Token only when at least one route is enabled; `startRefresh()` handles token changes; `revoke()` or registration with no enabled routes revokes the authenticated installation. Its injected `AuthenticatedNotificationGateway` must bind the installation to the verified session, support `revokeCurrentInstallation()` even after an app restart, verify every route belongs to that user, and never trust client-supplied ownership. It is intentionally not called by the app today. `setAuthenticatedNotificationTargetResolver()` can later resolve a remote alert's route IDs through that authenticated API when the route is not available locally. The local copy stays available when backend sync fails. Once backend delivery is confirmed for a route, call `setRemoteDelivery(routeId, true)` to cancel local duplicates; call it with `false` if remote delivery is withdrawn or the user signs out. No route is remote-managed by default.

## Remote push and backend status

**Remote push delivery and background obstacle monitoring are not active.** This branch has no authentication, route owner field, deployed push endpoint, route-relevance worker, EAS project ID, or confirmed FCM credentials. The existing `public.routes` policy allows anonymous access, so it cannot establish private route ownership. Do not store push tokens or preferences in that public table and do not enable a sender against it. The preparatory migration at `supabase/migrations/20261016170000_notification_private.sql` creates private service-role-only settings, device, and idempotent delivery tables with RLS and no anonymous/authenticated policies. It has **not been executed**. It does not send notifications by itself.

Before enabling remote delivery:

1. Coordinate authentication and `routes.owner_id` plus owner-only route/waypoint RLS with the routes teammate. Verify old anonymous route access is removed. Apply the private notification migration only after review and approval.
2. Configure an EAS project and Android FCM v1 credentials. Build a development app; Android remote push is unavailable in Expo Go. Keep service-role keys and any Expo push access token in server-side secrets only.
3. Implement the authenticated gateway behind `remote.ts`: verify JWT and route ownership on every preference write/route lookup; register/revoke tokens server-side; migrate local settings only after successful writes without clearing the local copy.
4. Connect the obstacle teammate's confirmed relevance output to a scheduled backend job. Use the data source's real update cadence; process new, changed, and cancelled construction records; queue one occurrence per user/route/obstacle/revision/kind in the private delivery table; check current opt-out and construction validity at send time.
5. Send from the server to Expo Push Service, inspect tickets and receipts, retry transient failures with backoff, deactivate `DeviceNotRegistered` tokens, and avoid duplicate local/remote scheduling once remote delivery takes ownership. Do not put addresses or tokens in logs.

No server-side construction job can safely determine affected routes until the obstacle interface and route ownership exist. Scheduled local reminders for **already known** events can still arrive while the app is backgrounded or closed, subject to OS settings; they do not discover new work while closed.

## Run and test

From `mobile/`: `npm ci`, then `npx expo start`. The gitignored `.env.local` needs `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to load real saved routes. Never put database or service-role secrets in `EXPO_PUBLIC_` variables. For a native Android build, use `npx expo run:android` with an Android SDK/device or configure EAS and run `npx eas-cli@latest build --profile development --platform android`. Rebuild a development binary after native-module/config changes. Local test alerts can run in Expo Go; remote push needs a development build and the backend setup above.

On a physical Android device, open **Notification Preferences** on a saved route, or the development-only `[TEST]` sample route if the route database is unavailable. Save each choice, custom time, and optional days; restart the app to verify persistence. The development preview shows a hypothetical future start date and resulting reminder time without changing production scheduling. Press **Send Test Construction Alert**, grant permission, and tap the labeled alert to check Google Maps. Repeat with the app foregrounded, backgrounded, and closed. Test denied permission and Disabled. Actual remote push must be tested separately after the backend and credentials are deployed.

Automated checks: `npm test -- --runInBand`, `npx tsc --noEmit`, `npx expo lint`, `npx expo-doctor`, and `npx expo export --platform android`. A JavaScript export is not an installable APK or a physical-device delivery test.
