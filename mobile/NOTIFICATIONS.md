# Issue #4: construction notifications

This is a local-notification MVP. Open **Notification Preferences**, choose a saved route, select **1 Week Before**, **1 Day Before**, or **Disabled**, then press **Save Preferences**. New routes default to Disabled. Settings are stored on this device in AsyncStorage under `@domove/construction-notifications/v1`, keyed by route ID. Expo schedules a 09:00 **device-local** reminder seven or one calendar day before the supplied construction start date. If the chosen time has passed, the start date is missing/invalid, or construction has ended, no reminder is scheduled. There is no late fallback alert.

## Integrating the team features

`src/notifications/model.ts` defines `NotificationRoute`, a structural subset of Issue #1's `SavedRoute`. The current read-only `listNotificationRoutes()` adapter loads Issue #1's `saved_routes` Supabase view. This view is created by Issue #1's migration, which must be present in the shared database; this branch does not copy route creation or deletion. The settings launcher is temporary: the routes teammate can render `<NotificationSettings route={savedRoute} onBack={...} />` from each route card and remove `NotificationsLauncher` from `App.tsx` after the route UI lands. On successful route deletion, call `await constructionNotifications.forgetRoute(route.id)` to remove its setting and cancel pending reminders.

The obstacle teammate calls `await constructionNotifications.processObstacle(savedRoute, event)` **only after** determining that the construction affects that route. The typed event is `ConstructionObstacleEvent` in `src/notifications/model.ts`. It needs a stable `routeId`, stable `obstacleId`, real `constructionLocation`, and actual `constructionStartDate` as `YYYY-MM-DD` in the site's local calendar. An optional end date, reliable `additionalMinutes`, and ordered `alternativeWaypoints` can be provided. Do not supply a travel-time estimate unless it has been calculated. The alternative waypoint list replaces the regular route's intermediate stops for Google Maps; up to three are passed in the universal URL for mobile-browser compatibility. Call `processObstacle()` again with the same IDs if dates/details change, or `removeObstacle(routeId, obstacleId)` if a site no longer affects the route. The service deduplicates against Expo's pending notification list, including after app restarts, and cancels outdated reminders when preferences or obstacle details change.

The notification payload contains a validated route snapshot so a tap can open directions even after the app was closed. The foreground response listener and initial response handler cover open, backgrounded, and cold-start taps. Google Maps Directions URLs include origin, destination, travel mode, and supported waypoints. Google Maps may choose its own path; the URL cannot guarantee an externally calculated detour. A web browser handles the same HTTPS URL when the Maps app is unavailable. Invalid route data is rejected.

There is **no server-driven push delivery** or automatic obstacle discovery while the app is closed. Existing Supabase construction data does not itself identify affected routes or send push messages. To add remote push later, a backend must detect route-specific changes, store user/device subscriptions and Expo/FCM/APNs tokens, respect each route's preference, and send the same route/event payload. There is intentionally no device-token registration yet because no delivery service or EAS project ID is configured. Scheduled local reminders for events already processed can arrive while the app is backgrounded or closed, subject to OS settings and delivery policy.

## Running and testing

From `mobile/`, run `npm ci` and `npx expo start`. Supply `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in the gitignored `.env.local` to load real saved routes. Never put the database password or secret key in `EXPO_PUBLIC_` variables. `npx expo run:android` requires an Android SDK/device; alternatively configure EAS and run `npx eas-cli@latest build --profile development --platform android`. Rebuild an existing development binary after adding the native notification and storage modules. Expo Go on Android includes local notifications and AsyncStorage, but **remote** push needs a development build; the existing Mapbox integration also needs a development build. Android 13+ asks for notification permission after the notification channel exists. Exact 09:00 delivery is subject to Android's alarm/notification policy; this app uses Expo's best-effort date trigger rather than requesting restricted exact-alarm permission.

On a physical Android device, open Notification Preferences. If the database has no routes, the development-only `[TEST]` sample route is available. Select each setting and save; relaunch to confirm persistence. For **1 Week Before** and **1 Day Before**, the development panel shows a hypothetical construction start and the resulting 09:00 reminder time without scheduling a fake construction event. Press **Send Test Construction Alert**, grant notification permission, wait a few seconds, and tap its `[TEST]` alert to verify Google Maps directions. Repeat with the app foregrounded, backgrounded, and closed. The test alert is explicitly labeled and is available only in development; it does not alter production scheduling or route preferences. On a real route, verify that Disabled causes the integration API to schedule nothing. Tests: `npm test -- --runInBand`, `npx tsc --noEmit`, `npx expo lint`, and `npx expo export --platform android`.
